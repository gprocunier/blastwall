Signed Evidence Reference Exemplar

blastwall v3

Privileged automation should be selected by policy, confined by SELinux, and trusted only after signed evidence verifies the host state.

blastwall v3 is the signed-evidence branch of Blastwall. IdM records the automation relationship, AAP gates launch, SELinux confines the managed-host session, and stable-v3 preflight verifies signed evidence before a selected host is trusted.

The branch is a reference exemplar: it shows how to operate the pattern in a real Calabi lab topology with IdM, AAP, KRA, and RHEL hosts. The original public site at blastwall.org remains the root entry point for the earlier Blastwall proof.

The 2-Minute Version

v3 changes the marker from proof into a locator. Inventory can use the marker to find candidate hosts, but preflight must retrieve the marker-referenced attestation, verify the signature, check the latest-generation index, and compare the signed claim with live host state.

That keeps the useful v1 and v2 shape - IdM, AAP, SELinux, profile registry, policy hashes, and managed-host probes - while adding a signed evidence gate before runtime work proceeds.

Marker Is Locator, Evidence Is Proof

v2 made host posture structured and release-checkable. v3 makes the trust boundary explicit: a host marker can help AAP select a candidate, but stable-v3 launch depends on signed evidence and live verification.

Reference Topology

The Calabi evidence path exercises workstation to virt-01 to bastion to IdM/AAP/KRA to managed host. It proves the reference path, failure behavior, custody wiring, and restoration flow for this exemplar.

Adopters should use the same shape as a guide, then assign their own ownership, retention, escalation, and scale evidence before presenting the pattern as a local operating control.

Why This Matters Now

Privileged automation moves quickly, broadly, and often with elevated access. v3 keeps the useful mitigation posture from the original proof while adding a signed evidence gate so host selection, launch, and audit all have a current proof surface.

Operating Loop

Useful posture does not end at policy installation. The v3 loop signs current evidence, stores it in KRA-backed vault paths, publishes a locator marker, uses inventory for selection, verifies evidence before launch, and audits scheduled state over time.

Adoption Path

Use this branch as an operating example, not as a claim that every environment is already covered. The implementation and Calabi evidence are ready as a reference exemplar. Local operation should add named owners, signer custody decisions, retention windows, escalation paths, and scale evidence appropriate to the adopter's environment.
